# Tickets

Every investigated failure ends in a Jira ticket (a new one, or a comment on the open one). The code is `agent/.../ticket.py`; the writes go through the Jira MCP server, the owner lookup through the GitHub MCP server.

## The ticket step is plain code, not an LLM

The step is a template over validated, structured results plus a lookup by fingerprint. Nothing in it needs judgment, so no model is involved (ADR 0006). It still runs as the `ticket_agent` identity: every call passes `policy/tools.py` (allowlist, repo pinning, argument size) and is written to the audit log, and it is the only identity that holds `create_issue` / `add_comment`.

## Flow

1. **Owners:** if the suspect commit is one the code investigator actually listed (same check as the fix gate), fetch its changed files and the repository's CODEOWNERS, and pick the assignee (below). Best effort: a missing CODEOWNERS file or a GitHub error leaves the ticket unassigned, never blocked.
2. **Search by fingerprint** (`search_similar_issues`).
3. **Open ticket found -> comment** ("New occurrence": build and commit links, category, this run's root cause and evidence, PR link or why no fix). The comment carries an idempotency key, so a redelivered event cannot add it twice.
4. **Otherwise -> create** a ticket from the template. Closed tickets with the same fingerprint do not block it; the new one says "Previously tracked (closed): DEMO-3".
5. If the create is refused because another worker just created the ticket (a race), search again and comment instead.

## Template

Summary (`[category] job: root cause`), Affected pipeline (job, build link, failing commit link, failed stage), Classification (category, confidence, fixable), Root cause, Evidence (bullets, suspect commit link, scrubbed log excerpt in a `{noformat}` block), Proposed fix (draft PR link, or the gate's reasons why none was attempted), Recommended next steps (by category, plus runbook steps found by the knowledge agent), Similar past incidents, Code owners, Fingerprint, and the footer *Generated by Pipeline Doctor — please verify.* The Jira MCP server takes wiki-style text; the real backend converts it to Atlassian Document Format by building nodes (never pasting text into markup).

## CODEOWNERS and assignment

`codeowners.py` implements GitHub's rules: the **last** matching pattern wins; `/x` or a middle slash anchors to the root, otherwise a pattern matches at any depth; `*` stays inside a segment, `**` crosses them; a pattern owns everything below it. The assignee is the *individual* who owns most of the files in the suspect commit (ties: first listed). Teams (`@org/team`) cannot be Jira assignees, so they are listed under "Code owners" instead. Mapping GitHub handles to Jira accounts is assumed identity in mock mode; real mode uses a reviewed JSON map (`JIRA_USER_MAP_FILE`) and leaves unmapped owners unassigned.

## Idempotency and failure handling

The queue is at-least-once, so every external effect is guarded (details in `worker/handler.py`):

| Risk | Guard |
|---|---|
| Same event delivered twice | `done:<key>` marker; `lease:<key>` for concurrent deliveries |
| Crash after the ticket is written, before "done" | `ticket:<key>` stores the outcome; a redelivery skips straight to "done" |
| Crash between the Jira write and `ticket:<key>` | the redelivered run finds the ticket by fingerprint; its comment has an idempotency key, so nothing is added twice |
| Two events for the same failure at once | per-fingerprint Redis lock (waits a few seconds, then retries later) plus the "already tracks this fingerprint" refusal in `create_issue` |

## Graceful degradation

If diagnosis fails (model unavailable, budget or timeout exceeded, invalid output) the message is retried. On the **final** attempt, instead of dead-lettering, a basic ticket is written: category `unknown`, the scrubbed log excerpt (re-fetched without any LLM), and the reason. Repeated outages of one job comment on one ticket (the fingerprint is stable per job when there are no facts). Only if Jira itself is unreachable does the message reach the DLQ, where the "DLQ not empty" alert (Phase 8) fires.

## Safety of what gets written

All text from builds, commits or models is scrubbed (again), stripped of Jira macros (`{noformat}`, `{code}`, `{panel}`, `{html}`...) and mention syntax (`[~user]`), made single-line where it sits in a sentence, and length-capped. The whole body is scrubbed once more as the last step, and the footer survives truncation. A hostile evidence string cannot reshape the ticket, mention a user, or smuggle a secret into Jira.

## Known limits

- A real Jira backend with ADF conversion exists (docs/mcp-servers.md) but has **never been run against a real Jira site**. Required custom fields and workflow transitions are not handled.
- The draft PR link comes from the fix flow (Phase 7) and is rendered when one exists.
- The lock release is get-then-delete (not atomic); the TTL bounds the damage.
- Comment idempotency relies on the Jira MCP server deduplicating by key; a real backend must preserve that (the marker is stored in the comment text).
